In your own frontend, each user trades with their own wallet. They sign in to get a session, and that session
plus the wallet is all `createTotalis` needs. How the pieces fit is on
[Your users' own wallets](/hyperliquid/build/partner-frontend).

## Sign in with a wallet

```ts
import { createTotalis } from "@totalis/hip4-client";
import { signInWithWallet, signOutWallet } from "@totalis/hip4-client/wallet-session";

const partnerKey = "tpb_v1_prd_...";

const session = await signInWithWallet({ environment: "production", signer: window.ethereum, partnerKey });

const totalis = createTotalis({
  environment: "production",
  accessToken: session.access_token,
  signer: window.ethereum,
  partnerKey,
});

// Later:
await signOutWallet({ environment: "production", accessToken: session.access_token, partnerKey });
```

`signInWithWallet` asks for a challenge, checks it is the Totalis sign-in for this origin, wallet and request,
has the wallet sign it, and returns the session.

Outside a browser, pass `origin` and send the same value as the `Origin` header with every request on the
session:

- A partner's wallet uses the partner's registered origin.
- A maker uses the Totalis app's origin: `https://app.totalis.trade`, or `https://hip4-staging.totalis.trade` on
  staging.

## Admit a wallet

A partner's wallet must be admitted before it can trade. The wallet consents in the browser, and your server
admits it with your `tpk_` key.

```ts
// Browser
import { signAdmissionConsent } from "@totalis/hip4-client/partner";

// chain_id comes from GET /v1/deployment.
const { address, consent } = await signAdmissionConsent({
  signer: window.ethereum,
  partner: "your-slug",
  environment: "production",
  chainId: deployment.chain_id,
});
```

```ts
// Server, with the address and consent the browser sent
import { createPartnerServer } from "@totalis/hip4-client/partner";

const partner = createPartnerServer({ environment: "production", serverKey: process.env.TOTALIS_PARTNER_KEY! });
await partner.admitWallet(address, consent);
```

`signAdmissionConsent` returns the wallet's `address` and its `consent`, and takes an optional
`lifetimeSeconds`. `createPartnerServer` refuses to run in a browser, so the server key cannot leak there. See [Partner frontend](/hyperliquid/build/partner-frontend).

## Deposit

| Function | Does |
| --- | --- |
| `totalis.directDepositCalls(amount)` | The approve and `depositUser` transactions for the wallet to send itself, paying its own gas |
| `totalis.signDeposit`, `totalis.sendDeposit` | A deposit the wallet signs and Totalis relays, paying the gas |

## Wallet approval

The [wallet approval](/hyperliquid/guides/trading#wallet-approval) lets entries with `funding: "approval"` draw
their shortfall from the wallet with no funding prompt. `openPosition` sets it when it needs to. To set, read or
revoke it yourself:

```ts
const approval = await totalis.readWalletApproval(); // { spender, approved, nonce, block, ... }
await totalis.approveWallet({ value: 50_000_000_000n, onSigned: (record) => save("approval", record) }); // 50,000 USDC
await totalis.revokeWalletApproval({ onSigned: (record) => save("approval", record) });
```

| Function | Does |
| --- | --- |
| `readWalletApproval()` | [Get wallet approval](/hyperliquid/api-reference/wallet-approval/get-wallet-approval): the approval left (`approved`) and the permit `nonce`, read at one block. `null` fields mean unread, never `0`. |
| `approveWallet({ value, onSigned })` | Signs a permit at the current nonce, awaits `onSigned` with the record, sends it and waits until it lands. Resolves with the `COMMITTED` request; throws `WalletApprovalError` when it changed nothing. `value` replaces the approval. |
| `revokeWalletApproval({ onSigned })` | `approveWallet` with `value` `0`. The approval ends only when this resolves. |
| `signWalletApproval({ value, approval })` | Signs a permit without sending it, at the nonce of `approval` or of a fresh read. Send it before its `deadline` ([Limits](/hyperliquid/limits-and-fees#limits)); one sent later is admitted and ends `PERMIT_EXPIRED`. |
| `sendWalletApproval(signed)` | Sends a signed permit under its request ID, and resends the same bytes after a lost answer. ([Wallet approval records](/hyperliquid/sdk/resume-and-retry#wallet-approval-records)) |
| `recoverWalletApproval(signed, { wait })` | Finishes a stored permit after a restart: resends it and follows it until it ends. Signs nothing. |

The signer must be the account's wallet: a vault agent cannot sign a permit. Use the SDK's revoke, not a token
`approve(0)` from another tool, which a signed permit that has not landed yet can undo
([What the approval allows](/hyperliquid/guides/trading#what-the-approval-allows)).

These functions serve the current vault's WalletAccept only. An approval left to an earlier vault's WalletAccept
cannot move funds once that vault is permanently retired on chain. The wallet clears it with its own `approve(0)` or
`permit(0)` ([What the approval allows](/hyperliquid/guides/trading#what-the-approval-allows)).

## Move cash to HyperCore

```ts
const exit = await totalis.exitToCore({ amount: 10_000_000n });
```

`exitToCore` moves vault cash to HyperCore. Store `exit.exit_id` if the process may restart: after one,
`waitForCoreExit(exitId)` follows it. `signCoreExit`
and `sendCoreExit` split it into sign and send.

`returnToCore()` takes no amount. It moves free vault cash and the wallet's available USDC (`WALLET_USDC` less
`pending.wallet_reserved`) back to HyperCore. Available wallet USDC under the sponsored deposit minimum
([Limits](/hyperliquid/limits-and-fees#deposits-and-exits)) stays in the wallet. `signReturnToCore` and
`sendReturnToCore` split it.

`returnToCore` throws for a Totalis app wallet (`wallet_kind: EMBEDDED` on `GET /v1/me`). A wallet embedded in
your own app is `EXTERNAL` and can use it. Staging runs no exits to HyperCore, so both functions throw
`ExitUnavailableError` there, before anything is signed.

## Vault agents

| Function | Does |
| --- | --- |
| `totalis.grantVaultAgent({ agent, validUntil })` | The wallet signs an `AgentGrant` for `agent` and Totalis relays it. Returns `operation_id`; follow it with `waitForOperation`. Needs a wallet session. |
| `totalis.revokeVaultAgent({ agent })` | The same with `validUntil` `0`. The agent keeps signing until its operation is `COMMITTED`. |
| `totalis.vaultAgents()` | The account's live agents, each with `valid_until` and `nonce`. Needs a wallet session. |
| `createTotalis({ ..., signer, agent })` | The agent signs `TakerAccept`, `SellBack`, `CashoutTransfer` and an `Exit` back to the account in place of `signer`. `signer` names the account and signs the rest. |

`agent` takes the same signer shapes as `signer`. Its grant rules, risk and a server-side setup are on
[Vault agents](/hyperliquid/build/partner-frontend#vault-agents).

## Issue a key from a session

`totalis.issueApiKey({ label, scopes })` issues the account's own `ttk_` key from a wallet session, with the
wallet's approval. `rotateApiKey` replaces one. Makers issue their keys with the `.../api-keys` helpers
instead ([Onboard headless](/hyperliquid/sdk/making#onboard-headless)).
