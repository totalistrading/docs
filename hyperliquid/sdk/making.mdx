`createMaker` runs a maker. It delivers every open RFQ, publishes your prices, and confirms each accept of a
price you published. You send one price per RFQ: Totalis fills in the other terms and keeps your quote takeable
until the RFQ closes or you replace or cancel it. The SDK never broadcasts a vault transaction: the maker wallet
sends those itself and pays the gas in HYPE. Set up your maker first
([Market making](/hyperliquid/guides/market-making#set-up)).

## A minimal bot

```ts
import { createMaker } from "@totalis/hip4-client/maker";
import { privateKeyToAccount } from "viem/accounts";

const makerId = process.env.TOTALIS_MAKER_ID!;
const maker = createMaker({
  environment: "production",
  apiKey: process.env.TOTALIS_MAKER_KEY!,
  makerId,
  signer: privateKeyToAccount(process.env.TOTALIS_WALLET_KEY as `0x${string}`),
});

maker.onRfq(
  async (rfq) => {
    if (rfq.kind === "ENTRY") {
      await maker.quote(rfq, { payout: (BigInt(rfq.stake) * 18n) / 10n }); // placeholder price
    } else if (rfq.maker_id === makerId) {
      await maker.bid(rfq, { price: 18_000_000n }); // buy back a position you back
    }
  },
  (error) => console.error(error),
);

process.once("SIGINT", async () => {
  await maker.close(); // cancels your open quotes, then closes the stream
  process.exit(0);
});
```

The SDK confirms every accept of a price this bot published. The prices are placeholders. Price from your own
market data ([Price entries](/hyperliquid/guides/market-making#price-entries)). `examples/node-bot.mjs` in the
package is a fuller version.

## Quote

### `onRfq(handler, onError?)`

Runs `handler` once per open RFQ per subscription, from both events and the snapshot.

- A restart or new subscription delivers the still-open RFQs again. Quoting again replaces your earlier quote,
  so it cannot double-fill.
- An RFQ where a taker's accept of your quote waits for your answer is held back, and offered again once it is
  answered.
- An RFQ you filled, or one that ended, is never offered again.
- `onError` receives whatever the handler throws, and the RFQ can be offered again.

### `quote(rfq, { payout })`

Publishes your payout on an entry RFQ and returns `{ quoteId }`. It replaces your previous quote on that RFQ.
Totalis fills in the other terms and keeps the quote takeable until the RFQ closes or you replace or cancel it.
Totalis renews the quote while it stands, and each renewal gives it a new ID. `cancelQuote` with any of them
cancels it.

It starts the stream and waits until it is live. After a truncated snapshot or a cursor resume, it first pages
[List acceptances](/hyperliquid/api-reference/quotes/list-acceptances), which needs `quote:read`.

### `bid(rfq, { price, legState })`

Publishes your price on a cash-out RFQ and returns `{ quoteId }`. Totalis fills in the other terms and keeps the
bid takeable until the RFQ closes or you replace or cancel it. Totalis sends a cash-out RFQ only to the maker
that backs the position ([Cash-outs](/hyperliquid/guides/market-making#cash-outs)).

A cash-out RFQ names the position (`position_id`), its owner as `taker`, your `maker_id`, its `legs`, `net_stake`
and `payout`. It carries no chain state: read the legs' state yourself, and pass it as `legState`. The SDK then
confirms only a sale at that leg state. Without `legState` it confirms at whatever leg state the accept carries,
which can differ from the one you priced if a leg resolved in between. Pass it whenever your price depends on the
legs' state, which for a cash-out it nearly always does.

```ts
import type { CashoutRfq } from "@totalis/hip4-client/maker";
import { signedLeg, totalisTypes } from "@totalis/hip4-client/typed-data";
import { concat, createPublicClient, hashStruct, http, keccak256, parseAbi, type Hex } from "viem";

const vaultAbi = parseAbi([
  "function tickets(bytes32 positionId) view returns (uint64 makerId, address owner, uint128 stake, uint128 payout, uint128 worst0, uint16 feeBps, uint8 status, uint128 residual, bytes32 legsHash)",
  "function legStateOf((uint32 outcomeId, uint8 side)[] legs, uint256 readGas) view returns (bytes32)",
]);
const chain = createPublicClient({ transport: http("https://rpc.hyperliquid.xyz/evm") });

async function bidOnCashout(rfq: CashoutRfq) {
  const vault = (await maker.deployment()).vault_address as Hex;
  const legs = rfq.legs.map(signedLeg);
  // The legs hash is the EIP-712 encoding of legs as Leg[]: check they are the position's.
  const legsHash = keccak256(concat(legs.map((leg) => hashStruct({ types: { Leg: totalisTypes.Leg }, primaryType: "Leg", data: leg }))));
  const [, , , , , , , , onChain] = await chain.readContract({ address: vault, abi: vaultAbi, functionName: "tickets", args: [rfq.position_id as Hex] });
  if (onChain !== legsHash) return;
  const legState = await chain.readContract({ address: vault, abi: vaultAbi, functionName: "legStateOf", args: [legs, 500_000n] });
  const price = priceCashout(rfq, legState); // your model; undefined to pass
  if (price !== undefined) await maker.bid(rfq, { price, legState });
}
```

`legStateOf` takes the legs and a read gas of `500000`. What its value encodes, and how to price from it, is on
[Price a cash-out](/hyperliquid/guides/market-making#price-a-cash-out). The sale lands only while every leg's state
still equals the one signed. If a leg moves first, the trade reverts and nothing moves.

While a taker's accept of your quote on the RFQ waits for your answer, `quote` and `bid` wait for that answer,
then publish.

### Cancel

| Function | Does |
| --- | --- |
| `cancelQuote(quoteId)` | Removes one quote. `ACCEPTED` means you already confirmed it. While an accept of it waits for your answer, the venue refuses with `STATE_CONFLICT`: decline the accept instead. |
| `cancelAllQuotes()` | Removes every open quote of this maker and answers `{ cancelled, pending }`. A quote whose accept waits for your answer stays, counted in `pending`. |
| `close()` | Cancels all your open quotes, then closes the stream. Await it before the process exits. It never rejects. |

Publish again to come back. A bot that stops without `close()` keeps its quotes up until it misses a confirm,
which withdraws all of them.

## Decline with a last look

The SDK confirms each accept of a price it published, signing the exact terms. To turn some down, for example
because the price moved, pass `lastLook`:

```ts
// stillGood is your own re-check of price and capital.
const maker = createMaker({
  // ...
  lastLook: async (acceptance) => ((await stillGood(acceptance)) ? "CONFIRM" : "DECLINE"),
  onConfirmError: (error, acceptance) => console.error(acceptance?.quote_id, error),
});
```

| Option | Default | Does |
| --- | --- | --- |
| `lastLook` | | Called with each accept before the SDK answers it. Return `"CONFIRM"` or `"DECLINE"`. Confirming a cash-out executes the owner-signed sale. |
| `autoConfirm` | `true` | `false` leaves every answer to another process, such as a separate confirmer that shares this bot's `published` store |
| `onConfirmError` | | Receives an answer that failed, with its accept |
| `published` | In memory | Where the SDK records what this maker published: the only terms it will sign. Pass durable storage so a restarted or separate process can confirm them. |

The SDK never answers an accept of a price it did not publish. It leaves that to the process that did.

### Answer accepts yourself

`onAcceptance(handler, onError?)` replaces the SDK's own answer while it is attached. It handles every pending
accept once, and resends a lost answer byte for byte. A handler that confirms terms this maker did not publish
gets an error, and nothing is sent. It must not await `quote` or `bid` on the accept's RFQ: those wait for its
answer.

`confirm(acceptance, decision)` answers one accept you read another way.

## Manage collateral

| Function | Does |
| --- | --- |
| `controller()` | Builds vault transactions: `approveUsdc`, `deposit`, `requestWithdraw`, `executeWithdraw`, `cancelWithdraw`, `resetDiscount`. Any wallet can fund a deposit (`approveUsdc`, `deposit`); the maker wallet sends the rest. |
| `withdrawal()` | The pending maker vault withdrawal, and what blocks executing it |
| `reduceCollateral({ signTransaction })` | Runs a [collateral reduction](/hyperliquid/guides/collateral#reduce-collateral) end to end |

`reduceCollateral` requests the reduction, follows it, and returns `{ job, idempotencyKey, submitted }`. With
`signTransaction`, it signs the certificate transaction and submits it. Without it, sign `job.transaction`
yourself and send it to [Submit self-funded transaction](/hyperliquid/api-reference/makers/submit-self-funded-transaction)
under the same `idempotencyKey`. Any wallet with HYPE can sign; the maker wallet works. It needs a key with the
maker collateral scopes.

See [Maker collateral](/hyperliquid/guides/collateral) for what a reduction frees.

## Onboard headless

A maker onboards and manages its keys from a wallet session, with no browser. Sign in with your Totalis account's
exported wallet and the Totalis app's origin ([Sign in with a wallet](/hyperliquid/sdk/wallets#sign-in-with-a-wallet)).
A partner-admitted wallet signs in with its partner's registered origin instead
([Partner-admitted wallet](/hyperliquid/guides/market-making#partner-admitted-wallet)).

`examples/onboard.mjs` in the package runs every step below, and resumes if you rerun it.

### Open the maker

| Function | Does |
| --- | --- |
| `openMakerVaultTransaction(deployment, address)` | The transaction that opens a maker for the wallet at `address`. Send it from that wallet, your account's wallet. |
| `makerReadiness(client)` | Reads and admits the account's maker (`GET` and `POST /v1/me/maker`), answering `NOT_INDEXED` until its open transaction is indexed |
| `waitForMaker(client)` | Polls `makerReadiness` until the maker is ready |

Both take a client signed in as the account (a wallet session), not a maker key.

### Issue the maker's keys

```ts
import { COLLATERAL_SCOPES, createApiKeyClient, issueApiKey } from "@totalis/hip4-client/api-keys";
import { toTotalisSigner } from "@totalis/hip4-client/signer";

const keys = createApiKeyClient("production", {
  accessToken: session.access_token,
  headers: { Origin: "https://app.totalis.trade" },
});
const owner = toTotalisSigner(wallet);

const quoting = await issueApiKey(keys, owner, {
  maker: makerId,
  label: "Quoting bot",
  preset: "MAKER", // QUOTING_BOT_SCOPES
  expires_in_days: 90, // 1 to 90, or 0 for no expiry; 30 when left out
});
const collateral = await issueApiKey(keys, owner, {
  maker: makerId,
  label: "Collateral",
  scopes: [...COLLATERAL_SCOPES], // no preset: list the scopes
  expires_in_days: 90,
});
```

| Function | Does |
| --- | --- |
| `issueApiKey(keys, owner, { maker, label, preset or scopes, expires_in_days })` | Asks for the maker's key challenge, checks it grants exactly the preset's or the listed scopes, has the maker wallet sign it, and creates the key. The secret is returned once. |
| `rotateApiKey(keys, owner, keyId, { maker, overlap_seconds })` | Replaces a key the same way. The old key keeps working for the overlap. |
| `listApiKeys(keys, { maker })` | Every key of the maker, oldest first, revoked and expired ones included |
| `revokeApiKey(keys, keyId, { maker })` | Revokes a key at once. No signature. |

Pass either `preset` or `scopes`, not both. `preset: "MAKER"` grants `QUOTING_BOT_SCOPES`, which move no vault
money; give it to the quoting bot. `COLLATERAL_SCOPES` has no preset: list it, on a separate key for reductions
([maker scope sets](/hyperliquid/authentication#scopes)). A refused request is `INVALID_REQUEST`, and its
`field_violations` names the entry it refused, `/preset` or `/scopes/<i>` (under `/request` when the challenge is
refused), with the reason in the message.
