A builder code names you on an RFQ. The positions it opens, and the fees they pay, count toward your revenue
share. Codes look like `tot_rfq_production_` followed by 32 hex characters, with `staging` in place of
`production` on [Staging](/hyperliquid/build/staging). Totalis issues them: see
[Get access](/hyperliquid/build/overview#get-access).

| Code | Scope | Signature |
| --- | --- | --- |
| Account code | Every account you admitted. One per environment. | None |
| Origin code | One of your registered origins | Your builder signer, per RFQ |

## Which code an RFQ records

| The account | `builder_code` you send | Recorded |
| --- | --- | --- |
| Admitted by you | None | Your account code |
| Admitted by you | One of your active codes for this environment | That code. A signature is optional; one you send must be your builder signer's. |
| Admitted by you | Another partner's code, or a revoked one | Refused |
| Admitted by another partner | Any of yours | Refused. The account is theirs. |
| Admitted by no partner | None | Nothing |
| Admitted by no partner | Your origin code, signed, from that origin | That code |
| Admitted by no partner | Your origin code without a signature, from another origin, or from an API key | Refused. Such an account's API key RFQs cannot be attributed. |

A refused code is `400 INVALID_REQUEST` with a field violation on `/builder_code`, and no RFQ is created. A code is
recorded once, when the RFQ is created, and never changes. Cash-out RFQs take no builder fields: a position keeps
the attribution of the RFQ that opened it.

An admitted account needs nothing from you on each RFQ. Signing is only for accounts you did not admit.

## Sign an origin code

For an account no partner admitted, an origin code works only on a browser request from its origin: a wallet
session that signed in on your page. An API key request carries no origin, so a signed code is refused there.
An account you admitted needs no origin code: its API key RFQs record your account code.

[Create RFQ](/hyperliquid/api-reference/rfqs/create-rfq) takes three extra fields:

```json
{
  "stake": "5000000",
  "legs": [{ "outcome_id": "1209", "side": "YES" }],
  "builder_code": "tot_rfq_production_0198a6f682a57abc9f2a4f0fb4374941",
  "builder_authorization_expiry": "1792152000",
  "builder_signature": "0x9e9e...9e1b"
}
```

| Field | Value |
| --- | --- |
| `builder_code` | Your origin code for the page's origin |
| `builder_authorization_expiry` | Unix seconds, in the future and within the [window](/hyperliquid/limits-and-fees#wallet-sign-in-and-partners) |
| `builder_signature` | Your builder signer's `personal_sign` of the message below, as lowercase hex |

The message is six lines joined by `\n`, with no trailing newline:

```text
Authorize Totalis RFQ builder attribution.
Environment: production
Participant: 0198a6f6-82a5-7abc-9f2a-4f0fb4374941
Idempotency key: 01a0df4e-5dc8-71f2-a3d4-c5b6a7988771
Request digest: 0x<SHA-256 hex>
Expiry: 1792152000
```

| Line | Value |
| --- | --- |
| `Environment` | `production`, or `staging` on staging |
| `Participant` | The account's `account_id`, from [Get identity](/hyperliquid/api-reference/account/get-identity) or the sign-in response |
| `Idempotency key` | The `Idempotency-Key` header of this Create RFQ request |
| `Request digest` | Lowercase hex SHA-256 of the request JSON below |
| `Expiry` | `builder_authorization_expiry`, as sent |

The request JSON is minified, with the keys in this order: `intent_id` and `intent_generation` only when you send
them, then `stake`, `legs`, `builder_code` and `origin`. Each leg is `{"outcome_id","side"}` in that order.
`origin` is the page's origin, exactly as the browser sends it in `Origin`. `intent_generation` is a decimal string.
Send the legs in strictly increasing `outcome_id` order, as Create RFQ requires.

```json
{"stake":"5000000","legs":[{"outcome_id":"1209","side":"YES"}],"builder_code":"tot_rfq_production_0198a6f682a57abc9f2a4f0fb4374941","origin":"https://app.example.com"}
```

Sign on your server, where the builder signer's key lives. Your page sends the RFQ terms (with `intent_id` and
`intent_generation` when the RFQ carries them), its chosen `Idempotency-Key` and the `account_id`; your server
checks them and returns the two fields.

```js
import { createHash } from "node:crypto";
import { privateKeyToAccount } from "viem/accounts";

const builder = privateKeyToAccount(process.env.TOTALIS_BUILDER_SIGNER_KEY);

export async function authorizeRfq({ accountId, idempotencyKey, intentId, intentGeneration, stake, legs, builderCode, origin, environment = "production" }) {
  const expiry = String(Math.floor(Date.now() / 1000) + 120);
  const request = JSON.stringify({
    ...(intentId === undefined ? {} : { intent_id: intentId }),
    ...(intentGeneration === undefined ? {} : { intent_generation: intentGeneration }),
    stake,
    legs: legs.map(({ outcome_id, side }) => ({ outcome_id, side })),
    builder_code: builderCode,
    origin,
  });
  const digest = createHash("sha256").update(request).digest("hex");
  const message = [
    "Authorize Totalis RFQ builder attribution.",
    `Environment: ${environment}`,
    `Participant: ${accountId}`,
    `Idempotency key: ${idempotencyKey}`,
    `Request digest: 0x${digest}`,
    `Expiry: ${expiry}`,
  ].join("\n");
  return { builder_authorization_expiry: expiry, builder_signature: (await builder.signMessage({ message })).toLowerCase() };
}
```

The SDK's `openPosition` does not send builder fields. Create the RFQ with `totalis.client.POST("/v1/rfqs")`
under the signed `Idempotency-Key`, then take a quote from `watchQuotes`, and sign and send it with `signEntry` and
`sendAcceptance` ([SDK](/hyperliquid/sdk/resume-and-retry)).

## Reports and payouts

Totalis pays you a share of the total fees on positions your codes opened, in USDC on HyperEVM, to the payout
address you registered. Your share is agreed with Totalis and recorded as terms: each terms entry prices every fee
from its UTC day until the next one.

Read your report from your server with your server key. It holds the figures Totalis pays from.

```bash
curl "https://hip4-api.totalis.trade/v1/partner/report?from=2026-10-01&to=2026-11-01" \
  -H "Authorization: Bearer $TOTALIS_PARTNER_KEY"
```

```ts
import { createPartnerServer } from "@totalis/hip4-client/partner";

const partner = createPartnerServer({ environment: "production", serverKey: process.env.TOTALIS_PARTNER_KEY });
const report = await partner.report({ from: "2026-10-01", to: "2026-11-01" });
```

| Field | Contents |
| --- | --- |
| `balance` | All time. `fees` charged on your positions; `accrued`, each terms period's fees times its share, rounded down; `paid`; and `owed`, which is `accrued - paid`. `unpriced_fees` were charged before your first terms and earn nothing. `share_bps` is your current share, in basis points. |
| `terms` | Every terms entry, oldest first: `effective_from` (a UTC day) and `share_bps`. |
| `days` | Each UTC day in the range with fees: positions opened (`tickets`), their stake, and the entry (`taker_fees`), winnings and cash-out (`buyback_fees`) fees, with the `share_bps` in force that day. |
| `totals` | The range's days added up. |
| `payouts` | Every payout to you, newest first: its period, payout address, `amount`, state, and each USDC transfer with its transaction hash, checked on-chain. |

| Range | Rule |
| --- | --- |
| `from`, `to` | UTC days (`YYYY-MM-DD`), sent together. `to` is exclusive: `from=2026-10-01&to=2026-11-01` is October. |
| Neither | The 30 days through today. |
| Longest | 366 days. Ask a longer period in parts. |

Amounts are atomic USDC decimal strings, 6 decimals: `"1500000"` is 1.50 USDC. A payout counts as paid in full
from the moment Totalis queues it; if less lands on-chain, the rest returns to `owed`. Totalis decides when to pay,
so `owed` is what you have earned and not yet been paid, not a schedule.

| Response | When |
| --- | --- |
| `200` | Your report |
| `400 INVALID_QUERY` | `from` or `to` is not a date, only one was sent, `from` is not before `to`, or they are more than 366 days apart |
| `401 UNAUTHENTICATED` | The server key is unknown or revoked, or your partner is suspended |
| `403 FORBIDDEN` | The request has an `Origin`, or a credential other than your server key. Read reports from your server. |
| `429 RATE_LIMITED` | More than 60 reports a minute |

A per-position list of fees, each with its transaction hash, is by email: ask
[founders@totalis.trade](mailto:founders@totalis.trade). To change your payout address, email us from your registered
contact.

## Rotation and revocation

| Change | Effect |
| --- | --- |
| A code is rotated | A new code replaces it. Send the new one; the old one is refused on new RFQs. |
| A code is revoked | Refused on new RFQs. RFQs and positions already created keep it. |
| Your builder signer is rotated | Signatures from the old signer are refused. |
| Your partner credentials are suspended | Every code of yours is revoked. Totalis reissues them when you are reinstated. |

To rotate a code or your signer, or to revoke a code, email
[founders@totalis.trade](mailto:founders@totalis.trade).
