A builder code names you on an RFQ. The positions it opens, and the fees they pay, count toward your revenue
share. Codes look like `tot_rfq_production_` followed by 32 hex characters, with `staging` in place of
`production` on [Staging](/hyperliquid/build/staging). Totalis issues them: see
[Get access](/hyperliquid/build/overview#get-access).

| Code | Scope | Attribution token |
| --- | --- | --- |
| Account code | Every account you admitted. One per environment. | None |
| Origin code | One of your registered origins | Minted on your server for each RFQ |

## When `builder_code` alone works

An account you [admitted](/hyperliquid/build/partner-frontend#onboard-a-user) is yours. Every RFQ it creates
records your account code, whatever credential it uses: a wallet session on your page, or an API key it issued.
You send nothing for that. To record a different code of yours, send it as `builder_code` alone; a
`builder_attribution` is optional there, and one you send must verify.

## When a token is needed

Any other account, one no partner admitted, such as a Totalis app user who signs in on your page with an
exported wallet key, is attributed only with your origin code and a `builder_attribution` token for that RFQ. You
mint the token on your server, where your builder signer's key lives.

The token is bound to the browser origin the RFQ comes from, and it must be one of your registered origins. A
wallet session carries the page's `Origin` on every request; an API key request carries none. So a token cannot
be used from an API key, or from a page that is not yours, and an API key RFQ from an account you did not admit
is never attributed to you. A copied token is no use elsewhere either: it covers one account, one
`Idempotency-Key`, and the exact stake, legs and code of one RFQ.

| The account | `builder_code` you send | Recorded |
| --- | --- | --- |
| Admitted by you | None | Your account code |
| Admitted by you | One of your active codes for this environment | That code. A token is optional; one you send must be your builder signer's. |
| Admitted by you | Another partner's code, or a revoked one | Refused |
| Admitted by another partner | Any of yours | Refused. The account is theirs. |
| Admitted by no partner | None | Nothing |
| Admitted by no partner | Your origin code, with a token, from that origin | That code |
| Admitted by no partner | Your origin code without a token, from another origin, or from an API key | Refused |

A refused code is `400 INVALID_REQUEST` with a field violation on `/builder_code`, and no RFQ is created. A code is
recorded once, when the RFQ is created, and never changes. Cash-out RFQs take no builder fields: a position keeps
the attribution of the RFQ that opened it.

### Mint a token

Your page picks the RFQ's `Idempotency-Key` and sends your server the RFQ exactly as it will create it. Your server
checks it, for example that the account is the user signed in to your page and the origin is yours, and mints the
token with `attributeRfq`:

```ts
// Server
import { attributeRfq, type AttributedRfq } from "@totalis/hip4-client/partner";
import { privateKeyToAccount } from "viem/accounts";

const builderSigner = privateKeyToAccount(process.env.TOTALIS_BUILDER_SIGNER_KEY as `0x${string}`);

export async function attribute(rfq: AttributedRfq): Promise<string> {
  // rfq: { participant, idempotencyKey, origin, request: { stake, legs, builder_code } }
  return attributeRfq({ ...rfq, signer: builderSigner }); // "<expiry>.<signature>"
}
```

| `attributeRfq` input | Value |
| --- | --- |
| `participant` | The account's `account_id`, from the sign-in response or [Get identity](/hyperliquid/api-reference/account/get-identity) |
| `idempotencyKey` | The `Idempotency-Key` the page will send with Create RFQ |
| `origin` | The page's origin, exactly as the browser sends it in `Origin` |
| `request` | `stake`, `legs` and `builder_code`, as the page will send them. Legs in strictly increasing `outcome_id` order. |
| `signer` | Your registered builder signer |
| `lifetimeSeconds` | Optional. Whole seconds, within the [limit](/hyperliquid/limits-and-fees#wallet-sign-in-and-partners). |

The token is `<expiry>.<signature>`: a Unix-second expiry and your signer's `personal_sign` of the message
`rfqAttributionMessage(rfq, expiry)` returns. It only has to be valid when the RFQ is created, so mint it right
before the page sends Create RFQ.

The page then creates the RFQ with the same key and request, and takes a quote with the step functions
([Entry and cash-out](/hyperliquid/sdk/resume-and-retry#entry-and-cash-out)). `openPosition` sends no builder
fields.

```ts
// Browser, signed in on your registered origin
import { unwrap, uuidv7 } from "@totalis/hip4-client";

const idempotencyKey = uuidv7();
const request = { stake: "5000000", legs: [{ outcome_id: "1209", side: "YES" as const }], builder_code: originCode };
const builder_attribution: string = await fetch("/api/attribute-rfq", {
  method: "POST",
  body: JSON.stringify({ participant: session.account_id, idempotencyKey, origin: location.origin, request }),
}).then((response) => response.json());

const { rfq_id } = unwrap(await totalis.client.POST("/v1/rfqs", {
  params: { header: { "Idempotency-Key": idempotencyKey } },
  body: { ...request, builder_attribution },
}));
const stop = totalis.watchQuotes(rfq_id, (quotes) => render(quotes));
```

### Revocation and existing RFQs

Attribution is decided once, when the RFQ is created. Revoking a code, rotating your builder signer, or a token
expiring afterwards never vetoes an RFQ already created: it stays open, its quotes can be accepted, and the
position it opens keeps your code. Revocation refuses only new RFQs ([Rotation and revocation](#rotation-and-revocation)).

## Reports and payouts

Totalis pays you a share of the total fees on positions your codes opened, in USDC on HyperEVM, to the payout
address you registered. Your share is agreed with Totalis and recorded as terms: each terms entry prices every fee
from its UTC day until the next one.

Read your report from your server with your server key. It holds the figures Totalis pays from.

```bash
curl "https://hip4-api.totalis.trade/v1/partner/report?from=2026-10-01&to=2026-11-01" \
  -H "Authorization: Bearer $TOTALIS_PARTNER_KEY"
```

```ts
import { createPartnerServer } from "@totalis/hip4-client/partner";

const partner = createPartnerServer({ environment: "production", serverKey: process.env.TOTALIS_PARTNER_KEY! });
const report = await partner.report({ from: "2026-10-01", to: "2026-11-01" });
```

| Field | Contents |
| --- | --- |
| `balance` | All time. `fees` charged on your positions; `accrued`, each terms period's fees times its share, rounded down; `paid`; and `owed`, which is `accrued - paid`. `unpriced_fees` were charged before your first terms and earn nothing. `share_bps` is your current share, in basis points. |
| `terms` | Every terms entry, oldest first: `effective_from` (a UTC day) and `share_bps`. |
| `days` | Each UTC day in the range with fees: positions opened (`tickets`), their stake, and the entry (`taker_fees`), winnings and cash-out (`buyback_fees`) fees, with the `share_bps` in force that day. |
| `totals` | The range's days added up. |
| `payouts` | Every payout to you, newest first: its period, payout address, `amount`, state, and each USDC transfer with its transaction hash, checked on-chain. |

| Range | Rule |
| --- | --- |
| `from`, `to` | UTC days (`YYYY-MM-DD`), sent together. `to` is exclusive: `from=2026-10-01&to=2026-11-01` is October. |
| Neither | The 30 days through today. |
| Longest | 366 days. Ask a longer period in parts. |

Amounts are atomic USDC decimal strings, 6 decimals: `"1500000"` is 1.50 USDC. A payout counts as paid in full
from the moment Totalis queues it; if less lands on-chain, the rest returns to `owed`. Totalis decides when to pay,
so `owed` is what you have earned and not yet been paid, not a schedule.

| Response | When |
| --- | --- |
| `200` | Your report |
| `400 INVALID_QUERY` | `from` or `to` is not a date, only one was sent, `from` is not before `to`, or they are more than 366 days apart |
| `401 UNAUTHENTICATED` | The server key is unknown or revoked, or your partner is suspended |
| `403 FORBIDDEN` | The request has an `Origin`, or a credential other than your server key. Read reports from your server. |
| `429 RATE_LIMITED` | More than 60 reports a minute |

A per-position list of fees, each with its transaction hash, is by email: ask
[founders@totalis.trade](mailto:founders@totalis.trade). To change your payout address, email us from your registered
contact.

## Rotation and revocation

| Change | Effect |
| --- | --- |
| A code is rotated | A new code replaces it. Send the new one; the old one is refused on new RFQs. |
| A code is revoked | Refused on new RFQs. RFQs and positions already created keep it. |
| Your builder signer is rotated | Tokens the old signer minted are refused on new RFQs. |
| Your partner credentials are suspended | Every code of yours is revoked. Totalis reissues them when you are reinstated. |

To rotate a code or your signer, or to revoke a code, email
[founders@totalis.trade](mailto:founders@totalis.trade).
