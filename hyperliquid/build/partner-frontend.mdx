Your users trade with their own wallet. The wallet is the Totalis account: it signs in once, then signs its own
bets, cash-outs and withdrawals. Totalis never holds the key, and you never hold the funds.

```bash
npm install @totalistrading/hip4-client@0.65.0 viem
```

The SDK is private: see [Get access](/hyperliquid/build/overview#get-access). It also explains how to request
your server key, browser key, registered origins and partner slug.

| Credential | Looks like | Where it lives | Does |
| --- | --- | --- | --- |
| Server key | `tpk_v1_prd_...` | Your server only. Secret. | Admits new wallets |
| Browser key | `tpb_v1_prd_...` | Your pages. Public. | Sent as `X-Totalis-Partner`. Selects your share of rate limits. Honoured only from your registered origins. |
| Registered origins | `https://app.example.com` | Totalis's records | The origins your users sign in from |
| Account code | `tot_rfq_production_...` | Totalis's records | Recorded on every RFQ from an account you admitted |

The SDK refuses to send a server key from a browser, and refuses a server key as the browser key. The API
refuses an admission that carries an `Origin` header.

## Onboard a user

<Steps>
  <Step title="The wallet consents to you, in your frontend">
    ```js
    import { createClient } from "@totalistrading/hip4-client";
    import { signAdmissionConsent } from "@totalistrading/hip4-client/partner";

    const { data: deployment } = await createClient("production").GET("/v1/deployment");
    const { address, consent } = await signAdmissionConsent({
      signer: window.ethereum, partner: "your-slug", environment: "production", chainId: deployment.chain_id,
    });
    // Send { address, consent } to your server.
    ```

    The wallet signs a `personal_sign` message naming your slug, the wallet, the environment, the chain and an
    expiry. It authorizes no financial action:

    ```text
    Allow your-slug to open a Totalis account for this wallet.
    This does not authorize a financial action.

    Wallet: 0x1111111111111111111111111111111111111111
    Partner: your-slug
    Environment: production
    Chain ID: 999
    Expires At: 2026-10-16T13:00:00Z
    ```

    The SDK sets the expiry an hour ahead; `lifetimeSeconds` changes it, within the
    [limit](/hyperliquid/limits-and-fees#wallet-sign-in-and-partners).
  </Step>
  <Step title="Your server admits the wallet">
    ```js
    import { createPartnerServer } from "@totalistrading/hip4-client/partner";

    const partner = createPartnerServer({ environment: "production", serverKey: process.env.TOTALIS_PARTNER_KEY });
    await partner.admitWallet(address, consent); // { address, admitted_at }
    ```

    | Case | Result |
    | --- | --- |
    | First admission | `200`, with `admitted_at` |
    | You admit the same wallet again | `200`, the first admission |
    | Another partner admitted it first | `409 STATE_CONFLICT`. The first partner keeps the wallet. |
    | The consent is for another partner, wallet, environment or chain, expired, or too far ahead | `422 INVALID_SIGNATURE` |
    | The request carries an `Origin` header | `403 FORBIDDEN`. Admit from your server. |
    | Your server key is revoked | `401 UNAUTHENTICATED` |
    | Too many admissions | `429 RATE_LIMITED`, with `Retry-After` |

    The call is [Admit wallet](/hyperliquid/api-reference/partners/admit-wallet).
  </Step>
  <Step title="The wallet signs in">
    ```js
    import { createTotalis } from "@totalistrading/hip4-client";
    import { signInWithWallet, signOutWallet } from "@totalistrading/hip4-client/wallet-session";

    const partnerKey = "tpb_v1_prd_...";
    const session = await signInWithWallet({ environment: "production", signer: window.ethereum, partnerKey });
    const totalis = createTotalis({ environment: "production", accessToken: session.access_token, signer: window.ethereum, partnerKey });
    ```

    The wallet signs a Sign-In with Ethereum message for this page's origin. It authorizes no financial action.
    The SDK checks the message names this origin, wallet and request before the wallet signs it. The first sign-in
    after admission creates the account.
  </Step>
  <Step title="The wallet trades">
    `totalis` has the same flows as any account: `openPosition`, `cashOut`, `withdraw`. See
    [Trading](/hyperliquid/guides/trading), [Withdrawals](/hyperliquid/guides/withdrawals) and the
    [SDK](/hyperliquid/sdk).
  </Step>
</Steps>

## Which wallets can sign in

| Wallet | Signs in |
| --- | --- |
| An EOA in an extension, such as `window.ethereum` | Yes. Your user sees a signature request for sign-in and for each signed action. |
| An embedded wallet you run, such as your own Privy app's | Yes. It signs without a popup. Totalis treats it as an external wallet: `wallet_kind: EXTERNAL`. |
| A contract wallet: Safe, smart account | No: `WALLET_CONTRACT_UNSUPPORTED`. Sign in with the EOA that controls it. |
| A wallet no partner admitted and with no account | No: `ACCESS_REQUIRED`, during the invite-only launch. Admit it first. |

The `signer` is any EIP-1193 provider, viem account or wallet client, or ethers signer. Trade signatures accept
ERC-1271, but sign-in does not.

A Totalis app user's wallet is embedded inside the Totalis app (`wallet_kind: EMBEDDED`), so they have no wallet to sign in with
on your site. To trade through your product they create an API key in the
[Totalis app](https://hip4.totalis.trade/account/api-keys), or export their wallet key
([Wallet key](/hyperliquid/authentication#wallet-key)). An account created in the Totalis app is not admitted by
you, so its RFQs are attributed to you only with a signed [origin builder code](/hyperliquid/build/builder-codes),
which needs the user to sign in on your page with their exported wallet key. RFQs it sends with an API key cannot be attributed to you.

## Sessions

The SDK calls [Create wallet challenge](/hyperliquid/api-reference/wallet-sessions/create-wallet-challenge),
[Create wallet session](/hyperliquid/api-reference/wallet-sessions/create-wallet-session) and
[End wallet session](/hyperliquid/api-reference/wallet-sessions/end-wallet-session).

| | |
| --- | --- |
| Token | `access_token`, a bearer token. Send it as `accessToken`. |
| Bound to | The origin it signed in from. Every request with it must carry that `Origin`. |
| Lifetime | Fixed maximum and idle limit on [Limits](/hyperliquid/limits-and-fees#wallet-sign-in-and-partners) |
| Refresh | None. Sign in again. |
| End | `signOutWallet`. Any later request with the token is `UNAUTHENTICATED`. |
| API keys | A session can issue, rotate and revoke the account's own `ttk_` keys (`totalis.issueApiKey` and `rotateApiKey`; revoke with `revokeApiKey` from `.../api-keys`), for a bot that trades the same account. |

A browser sets `Origin` itself. Outside a browser, pass `origin`, one of your registered origins, to
`signInWithWallet` and `signOutWallet`, and send it as the `Origin` header on every later call and stream
(`headers` on `createTotalis`).

```js
const origin = "https://app.example.com";
const session = await signInWithWallet({ environment: "production", signer: account, partnerKey, origin });
const totalis = createTotalis({
  environment: "production", accessToken: session.access_token, signer: account, partnerKey, headers: { Origin: origin },
});
```

## Origins and CORS

The API answers CORS from your registered origins. Preflights allow `Authorization`, `Content-Type`,
`Idempotency-Key`, `traceparent` and `X-Totalis-Partner`, and expose `Idempotency-Replayed`, `Retry-After` and
`X-Request-ID`.

| You send | Result |
| --- | --- |
| A request from a registered origin | Answered with `Access-Control-Allow-Origin` set to it |
| Sign-in or a preflight from an origin Totalis has not registered | `403 ORIGIN_NOT_ALLOWED` |
| A session token from another origin, or with no `Origin` | `401 UNAUTHENTICATED` |
| A browser key from an origin that is not yours, or an unknown or revoked key | `403 FORBIDDEN` |

To add or remove an origin, email [founders@totalis.trade](mailto:founders@totalis.trade).

## Funding

| From | How | Who pays gas |
| --- | --- | --- |
| The wallet's USDC on HyperEVM, at bet time | Automatic. `openPosition` funds any vault shortfall from the wallet in the same accept. | Totalis |
| The wallet's spot USDC on HyperCore, at bet time | Pass `core`, the HyperCore USDC you offer, to `openPosition` or `signEntry`. Free vault cash goes first, then the wallet's HyperEVM USDC. The wallet signs a Hyperliquid `sendAsset` that bridges the rest to its HyperEVM address. The SDK sends it only after the maker confirms ([Funding from HyperCore](#funding-from-hypercore)), and the trade funds from the wallet. 0.05 USDC stays on HyperCore for the bridge's gas. Pass `core: null` when your HyperCore read failed. | The wallet, from the 0.05 USDC it keeps on HyperCore |
| The wallet's USDC on HyperEVM, ahead of time | `signDeposit` then `sendDeposit`: a USDC authorization Totalis relays into the vault ([Create deposit](/hyperliquid/api-reference/deposits/create-deposit)). Size and rate [limits](/hyperliquid/limits-and-fees#deposits-and-exits) apply. | Totalis |
| The wallet's USDC on HyperEVM, ahead of time, self-sent | `directDepositCalls(amount)` returns an approve and a `depositUser` transaction. The wallet sends them with its own provider. The balance and activity show the deposit with no API call. | The wallet |

```js
const calls = await totalis.directDepositCalls(10_000_000n); // 10 USDC
for (const call of calls) await walletClient.sendTransaction(call);
```

## Signatures and quote life

An entry takes one to three signatures, depending on where the stake comes from. `signEntry` asks for all of them
at the press, before anything is sent. A wallet that prompts shows them one after another.

| The stake comes from | The wallet signs | Prompts |
| --- | --- | --- |
| Free vault cash | `TakerAccept` | 1 |
| The wallet's HyperEVM USDC, for some or all of it | `TakerAccept`, USDC `ReceiveWithAuthorization` | 2 |
| The wallet's HyperCore USDC, for what HyperEVM lacks (`core`) | `TakerAccept`, Hyperliquid `SendAsset`, USDC `ReceiveWithAuthorization` | 3 |

Every one of them, the Hyperliquid bridge included, names the deployment's chain: `chain_id` in
[Get deployment](/hyperliquid/api-reference/deployment/get-deployment), `999` in production and `998` on staging.
Some extension wallets refuse to sign for a chain other than the one they are on. Switch the wallet to HyperEVM
before the first prompt.

An entry quote can be accepted until its `accept_before` ([Limits](/hyperliquid/limits-and-fees)), which leaves
time for the maker to confirm and the trade to land. The RFQ's own `expires_at` only stops new quotes. Every
prompt, and every round trip to a server signer, spends the time left, so sign at once. `bestQuote()` keeps the
highest payout whose `accept_before` is still ahead on the venue's clock. To keep a margin for your signer, filter
first:

```js
import { bestQuote } from "@totalistrading/hip4-client";

const marginMs = 3_000; // your signer's worst case
const choose = (quotes, serverNowMs) =>
  bestQuote()(quotes.filter((quote) => Date.parse(quote.accept_before) - serverNowMs > marginMs), serverNowMs);

await totalis.openPosition({ legs, stake, core, cash, choose, onSigned: save });
```

`serverNowMs` is the venue's clock. To pick from your own list, pass that clock:
`bestQuote()(quotes, totalis.stream.serverNow())`, or the `serverNowMs` that `watchQuotes` gives you. Pass `cash`,
a `spendableCash` read you already hold, to skip a balances read on the press.

### Funding from HyperCore

The bridge and the accept are separate. The bridge is a HyperCore action that moves USDC from the user's
HyperCore spot balance to their wallet on HyperEVM. The accept is the HyperEVM transaction that takes the stake.
The SDK signs both at the press and saves them, posts the accept first, and decides on the bridge from the answer:

| The accept | The bridge |
| --- | --- |
| `ACCEPTED`, `fund_by` still ahead | Sent, and resent while unanswered, until `fund_by` |
| `ACCEPTED`, `fund_by` passed | Discarded. The trade fails unless the wallet already holds the cash. |
| `DECLINED`, `TIMED_OUT`, `CANCELLED`, `NOT_ADMITTED`, or refused | Discarded. Nothing moved. |

`fund_by` is on [Limits](/hyperliquid/limits-and-fees). The SDK judges it on the venue's clock, never the device's.
If the wallet still lacks the funding when the trade is sent, nothing trades: the operation ends
`EXPIRED_UNEXECUTED` with `failure_reason` `INSUFFICIENT_CASH`, and the RFQ ends `FAILED` with `terminal_reason`
`INSUFFICIENT_CASH`.

An accepted entry can also fail after its bridge landed: the operation ends `REVERTED` or `EXPIRED_UNEXECUTED`.
Nothing trades and the vault takes nothing, but the bridged USDC is now in the wallet on HyperEVM, not on
HyperCore. Get balances shows it as `WALLET_USDC`, and `bridged` on the result names the amount. Show it as wallet
cash rather than as gone. When Hyperliquid did not confirm the bridge in time, the trade fails for want of cash
with the USDC on HyperCore or in the wallet; read balances to know which. `entryFailure` tells that apart from
plain not enough cash ([Open a position](/hyperliquid/sdk#open-a-position)).

| You want | Do |
| --- | --- |
| The user to bet again | Nothing. The next entry funds from that wallet USDC first. |
| The cash back on HyperCore | `returnToCore()` ([Moving cash to HyperCore](#moving-cash-to-hypercore)) |

A bridge whose answer never arrived can still land after the SDK stops resending it at `fund_by`. Read the
balances to learn where the cash is; never infer it from a missing answer.

### Recovery after a crash or reload

Persist every record `onSigned` or `onRecord` gives you, keyed by the user, and save each later version over the
last. If your server signs for users, keep the records on your server, not on the device. After a crash, a reload
or an app kill, finish each unfinished record:

```js
const result = await totalis.recoverAcceptance(record, { onRecord: save });
```

It signs nothing. It reads the acceptance, sends a never-sent bridge only while the acceptance is `ACCEPTED`
before `fund_by`, resends a sent bridge with the same bytes until `fund_by`, and discards the rest. Then follow
`operationId` until it is terminal, and treat only `COMMITTED` as a trade.

## Moving cash to HyperCore

An external wallet's vault cash, including a wallet embedded in your own app, is not swept to HyperCore in the background. Before a native HyperCore order,
move it:

```js
const exit = await totalis.exitToCore({ amount: 5_000_000n });
await totalis.waitForCoreExit(exit.exit_id); // resolves once HyperCore credits it
```

The wallet signs an `Exit`, and Totalis pays the gas ([Create HyperCore exit](/hyperliquid/api-reference/core-exits/create-hypercore-exit),
[Get HyperCore exit](/hyperliquid/api-reference/core-exits/get-hypercore-exit)). One move at a time per account: another is
`CORE_MOVE_IN_FLIGHT`.

`returnToCore()` moves all of the account's available cash back together: free vault cash, plus the wallet's
available USDC on HyperEVM. Available wallet USDC is `WALLET_USDC` less `pending.wallet_reserved`
([Get balances](/hyperliquid/api-reference/account/get-balances)); USDC reserved for work in flight stays in the
wallet. It takes no amount. The wallet signs a USDC `ReceiveWithAuthorization` that deposits its available USDC
into the vault, then one `Exit` of that plus the free vault cash. Totalis pays the gas for both, so the wallet
needs no HYPE. When the available wallet USDC is under the
[sponsored deposit minimum](/hyperliquid/limits-and-fees#deposits-and-exits), it stays in the wallet and
only the free vault cash moves. To move a chosen amount, use `exitToCore`.
Staging runs no exits to HyperCore, so `exitToCore` and `returnToCore` fail there
([Staging](/hyperliquid/build/staging#what-staging-does-not-run)).

The first credit to a HyperCore account that does not exist yet pays Hyperliquid's activation fee, so it has a
higher minimum ([Limits](/hyperliquid/limits-and-fees#deposits-and-exits)). Until the user accepts that
1 USDC fee, `exitToCore` and `returnToCore` fail with `409 CORE_ACCOUNT_ACTIVATION_REQUIRED`. Pass
`activationFeeAccepted: true` once they accept it.

## Withdrawals

Withdrawals and exits to HyperCore are sponsored. For an account that signs in with an external wallet they share
one minimum and one hourly count ([Limits](/hyperliquid/limits-and-fees#wallet-sign-in-and-partners)).

| Case | Result |
| --- | --- |
| Below the minimum | `400 INVALID_REQUEST`, naming the amount field |
| Over the hourly count | `429 RATE_LIMITED`, with `Retry-After` |

## Every signature

Each action the wallet signs, and what it signs. Typed data is `eth_signTypedData_v4`; the full domains and types
are on [Domain](/hyperliquid/authentication#domain) and [Types](/hyperliquid/authentication#types). Read the
values from [Get deployment](/hyperliquid/api-reference/deployment/get-deployment).

| Action | SDK | Message | `chainId` | `verifyingContract` |
| --- | --- | --- | --- | --- |
| Consent to your partner slug | `signAdmissionConsent` | `personal_sign` | In the text | |
| Sign in | `signInWithWallet` | `personal_sign` (Sign-In with Ethereum) | In the text | |
| Issue an API key | `issueApiKey`, `rotateApiKey` | `personal_sign` (Sign-In with Ethereum) | In the text | |
| Accept an entry | `openPosition`, `signEntry` | `TakerAccept` | `chain_id` | `vault_address` |
| Fund an entry from the wallet | `openPosition`, `signEntry` | `ReceiveWithAuthorization` | `usdc.eip712_domain.chain_id` | `usdc.address` |
| Bridge from HyperCore for an entry | `openPosition`, `signEntry` with `core` | `HyperliquidTransaction:SendAsset` | `chain_id` | `0x0000000000000000000000000000000000000000` |
| Cash out | `cashOut`, `signCashout` | `SellBack` or `CashoutTransfer` | `chain_id` | `vault_address` |
| Withdraw: vault leg | `withdraw`, `signWithdrawal` | `Exit` | `chain_id` | `vault_address` |
| Withdraw: payout | `withdraw`, `signWithdrawal` | `TransferWithAuthorization` | `usdc.eip712_domain.chain_id` | `usdc.address` |
| Deposit, sponsored | `signDeposit` | `ReceiveWithAuthorization` | `usdc.eip712_domain.chain_id` | `usdc.address` |
| Exit to HyperCore | `exitToCore`, `signCoreExit` | `Exit` | `chain_id` | `vault_address` |
| Return to HyperCore | `returnToCore`, `signReturnToCore` | `ReceiveWithAuthorization`, then `Exit` | As above | As above |
| Deposit, self-sent | `directDepositCalls` | Two transactions: `approve` to `usdc.address`, `depositUser` to `vault_address` | `chain_id` | |

The bridge's domain is Hyperliquid's: its `verifyingContract` is the zero address. If your signing policy
allowlists verifying contracts, add the zero address on `chain_id` for `HyperliquidTransaction:SendAsset` only.

### Signing on your server

If your server signs for your users, for example through a server wallet API such as Privy's, your server is
the only thing between a user's click and their money. A policy that allows a primary type allows every message
of that type: an allowed `TransferWithAuthorization` pays anyone.

- **Sign only the message you built.** For each request, build the expected typed data on your server, for the
  authenticated user and the action they confirmed in your UI, with the SDK's [builders](/hyperliquid/sdk#signing).
  Sign only when the request equals it in full: domain, primary type and every field, the nonce included.
  Comparing the two `hashTypedData` digests checks all of it at once. Checking a few fields is not enough: a
  deposit names the account it credits only inside its nonce.

  | Message | Build it from |
  | --- | --- |
  | `TakerAccept` | The `entry` terms of the quote the user chose, with `taker` the user's wallet |
  | `ReceiveWithAuthorization` | `from` the user's wallet, `to` `vault_address`, and the `value` the user approved. The `nonce` is `depositNonce`, derived from `vault`, `chainId`, `from`, `salt` and `account` ([USDC nonces](/hyperliquid/authentication#usdc-nonces)). `account` is the vault balance the deposit credits and appears nowhere else in the message. Derive the nonce yourself with the user's wallet as both `from` and `account`; never sign a nonce you did not derive. |
  | `SendAsset` | `bridgeAction` for the amount the user approved. Its `destination`, `0x2000000000000000000000000000000000000000`, credits the signer's own HyperEVM address. |
  | `SellBack`, `CashoutTransfer` | The terms of the bid the user chose, with the owner or seller the user's wallet |
  | `Exit` | `account` the user's wallet, and the `amount` the user approved. `to` is the user's wallet for a withdrawal, or `deployment.router_address` from `GET /v1/me/core-exits` for an exit to HyperCore. |
  | `TransferWithAuthorization` | `from` the user's wallet, and the `to` and `value` the user entered. The `nonce` is `payoutNonce`, derived from the user's wallet and the withdrawal's `Idempotency-Key`, which binds the payout to that one withdrawal. Derive it yourself. |

- **One user, one signer.** Resolve the wallet from the user's own authenticated request every time. Never fall
  back to a shared or default wallet. Each user signs in with their own wallet and keeps their own Totalis session
  token.
- **Policies are a backstop, not the check.** Restrict `chainId` and `verifyingContract` per message as in the
  table above. A policy that compares message fields against a `types` map needs that map exactly as your signer
  sends it.

The SDK passes each message to the `signer` you give it, so a server signer is any viem account, viem wallet
client or ethers signer that calls your wallet API.

## Attribution and revenue share

An account you admit is yours for good. The partner is fixed when the account is created, so a copied browser key
cannot move it to another partner. Every RFQ from the account records your account code, whatever credential it
uses: its session, or an API key it issued. Its requests spend your share of rate limits.

Payouts, reports and other accounts are on [Builder codes](/hyperliquid/build/builder-codes).

## If something is switched off

| Switched off | What your users see | What still works |
| --- | --- | --- |
| External wallets, during an incident | Sign-in, sessions and the API keys of wallet-only accounts get `AUTHORIZATION_UNAVAILABLE`, retry `BACKOFF`. Open streams close. | Signing out. Sessions work again once it is back on. |
| Your partner credentials | Your server keys, browser keys and origins stop working, and admissions stop. Your codes are revoked; Totalis reissues them when you are reinstated. | Your users' funds stay in their own wallets and vault balances. |

Accounts in the Totalis app are never affected.

## Errors

Every code is on [Errors](/hyperliquid/errors#codes). These come from sign-in, sessions and admission.

| Code | HTTP | Retry | Meaning |
| --- | ---: | --- | --- |
| `ACCESS_REQUIRED` | 403 | `NEVER` | The wallet has no account and no partner admitted it. Admit it, then sign in again. |
| `WALLET_CONTRACT_UNSUPPORTED` | 422 | `NEVER` | The address holds contract code. Sign in with the EOA that controls it. |
| `ORIGIN_NOT_ALLOWED` | 403 | `NEVER` | The origin is not one Totalis registered for you. |
| `ORIGIN_REQUIRED` | 400 | `NEVER` | A sign-in or session command needs exactly one `Origin` header. |
| `INVALID_SIGNATURE` | 422 | `NEVER` | The sign-in signature is wrong, expired, for another origin or chain, or already used. Or the admission consent does not verify. |
| `STATE_CONFLICT` | 409 | `REFRESH` | Admission: another partner admitted the wallet. Sign-in: request a new challenge. |
| `UNAUTHENTICATED` | 401 | `NEVER` | The session ended, expired or idled out. Sign in again. |
| `AUTHORIZATION_UNAVAILABLE` | 503 | `BACKOFF` | Sign-in is unavailable, or external wallets are switched off. |
| `RATE_LIMITED` | 429 | `BACKOFF` | Wait `Retry-After` seconds. |
