Totalis pushes every change to your account or your maker over one WebSocket, `totalis.realtime.v2`.
You send one `subscribe` frame and receive `{channel, data}` frames. The SDK flows run on it and read
over HTTP only to recover. Build the same way: use the HTTP reads to recover, not to poll.

What each subscription carries is on its own page:

| Subscription | Key | Page |
| --- | --- | --- |
| `account` | Personal key | [Account subscription](/hyperliquid/account-stream) |
| `maker` | Maker key | [Maker subscription](/hyperliquid/maker-stream) |

Public market prices use a separate stream: [Market data stream](/hyperliquid/market-stream).

## Connect

| | Value |
| --- | --- |
| URL | `wss://hip4-api.totalis.trade/v1/stream` (staging: `wss://hip4-api-staging.totalis.trade/v1/stream`) |
| Subprotocol | `totalis.realtime.v2` |
| Server clients | Send `Authorization: Bearer <key>` on the upgrade. |
| Browsers | Cannot set headers. Request a second subprotocol, `auth.<base64url of the key>`, from an allowed origin. The server selects only `totalis.realtime.v2`. |
| Reference | [Open stream](/hyperliquid/api-reference/streams/open-stream) |

The key never goes in the URL.

## Subscribe

Send exactly one frame after the upgrade. There is no unsubscribe: close the socket.

```json
{ "method": "subscribe", "subscription": { "type": "account" } }
```

A malformed or late frame closes the socket with `INVALID_SUBSCRIPTION`. A subscription or option your
key may not use closes it with `SUBSCRIPTION_DENIED`. The fields of each subscription type are on its
page.

## Frames

Every server frame is `{ "channel": ..., "data": ... }`:

| `channel` | When | `data` |
| --- | --- | --- |
| `subscriptionResponse` | Once, right after your subscribe | Your subscription echoed without its cursor, plus `connection_id`, `server_time`, `heartbeat_interval_ms`, `resume` and `cursor` |
| `snapshot` | After the response, when `resume` is `SNAPSHOT` or `RESET` | `cursor`, `resources`, and `truncated` when a class was cut short |
| `event` | Each committed change, in order | `cursor`, `event_id`, `event_type`, `occurred_at`, `payload` |
| `publication` | Each heartbeat, with `publication_freshness` | A checkpoint: `cursor`, `source_cut_at`, `server_time` |
| `readInvalidated` | With `account_reads`, when an account read changed | The `resources` to read again |
| `marketRefresh` | After the snapshot, and when the market catalog changes | `catalog_generation`, `resource: "/v1/markets"`. Read the market list again. |
| `drain` | The server is restarting | `deadline`, `retry_after_ms` |
| `reset` | Right before the server closes with `CURSOR_RESET` | None |

An event frame:

```json
{
  "channel": "event",
  "data": {
    "cursor": {
      "stream_id": "0199a1c2-3b4d-7e5f-8a6b-1c2d3e4f5a60",
      "generation_id": "0199a1c2-3b4d-7e5f-8a6b-1c2d3e4f5a61",
      "sequence": "184241"
    },
    "event_id": "0199a1c9-1b22-7d4e-8f31-6c8d9eafb002",
    "event_type": "OPERATION_UPDATED",
    "occurred_at": "2026-09-26T20:00:02.905114Z",
    "payload": {
      "operation_id": "0x5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e5e",
      "kind": "ACCEPT",
      "status": "COMMITTED",
      "transaction_hash": "0xa7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7a7",

```

`event_type` selects the shape of `payload`. Ignore event types you do not recognize.

## Snapshots and truncated

Without a cursor, the `snapshot` frame holds your current live state, keyed by class, and the cursor it
is consistent with. Replace your local state with it, then apply events after that cursor. Each class
holds at most a fixed number of items (see [Limits](/hyperliquid/limits)). A class cut short is listed in
`truncated` with the HTTP route that pages the rest:

```json
{ "resource": "acceptances", "href": "/v1/makers/7/acceptances" }
```

Page that route once, as described on [Pagination](/hyperliquid/pagination). Balances, positions and
maker capital are not snapshot classes: read them over HTTP when you connect, and again on their events.

## Apply events

Delivery is at least once. Skip an event whose `event_id` you have seen or whose `cursor.sequence` is
not above your cursor. Apply events in `sequence` order. Sequences can skip numbers, since other
accounts' events are filtered out, so never treat a skipped number as a gap. Persist the event's
`cursor` only after you have applied it.

## Resume

Send your last applied cursor in the subscription. Resuming needs `replay:read`.

```json
{
  "method": "subscribe",
  "subscription": {
    "type": "account",
    "cursor": {
      "stream_id": "0199a1c2-3b4d-7e5f-8a6b-1c2d3e4f5a60",
      "generation_id": "0199a1c2-3b4d-7e5f-8a6b-1c2d3e4f5a61",
      "sequence": "184241"
    }
  }
}
```

| `resume` in `subscriptionResponse` | Do |
| --- | --- |
| `REPLAY` | The events after your cursor follow. Apply them in order. |
| `SNAPSHOT` | You sent no cursor. Replace your local state with the snapshot that follows. |
| `RESET` | Your cursor is too old, ahead, or from another generation. Discard your local state and apply the snapshot that follows. |

The stream is the only replay. There is no HTTP event log. The replay window is on
[Limits](/hyperliquid/limits).

## Heartbeats, drains and closes

`heartbeat_interval_ms` is `15000`, or `1000` with `publication_freshness`. Keepalive is WebSocket
ping and pong. On `drain`, open a replacement connection, resume from your last applied cursor, then
close the old one; the server closes it with `CONNECTION_DRAIN` by the `deadline`.

Every other close carries a code from [Errors](/hyperliquid/errors) as its reason, and the code's
`retry` says what to do:

| `retry` | Do |
| --- | --- |
| `BACKOFF` | Reconnect with backoff and resume from your cursor. `SLOW_CONSUMER` and `CONNECTION_DRAIN` are this. |
| `REFRESH` | Reconnect without a cursor and apply the fresh snapshot. A `reset` frame means this. |
| `NEVER` | Stop. The key or subscription is not allowed, for example `SUBSCRIPTION_DENIED` or `AUTHORIZATION_REVOKED`. |

## With the SDK

`TotalisStream` does all of the above: it sends the subscribe, applies the snapshot or replay, drops
duplicates, and reconnects with jittered backoff from the last applied cursor.

```ts
import { TotalisStream } from "@totalistrading/hip4-client/realtime";

const stream = new TotalisStream({
  environment: "production",
  accessToken: process.env.TOTALIS_API_KEY!,
  subscription: { type: "account" }, // or { type: "maker", maker_id: "7" }
});
stream.on("status", (status) => console.log(status)); // connecting, live, disconnected, closed
stream.on("snapshot", (snapshot) => console.log("replace local state", snapshot.cursor));
stream.on("reset", () => console.log("local state is void; a snapshot follows"));
stream.on("event", (event) => console.log(event.event_type, event.payload));
stream.start();
```

`status` is `live` only while subscribed and caught up, so treat anything built from the stream as stale
otherwise. `stream.cursor` is the last applied cursor: pass it back as `cursor` to resume after a
restart. `createTotalis` and `createMaker` each hold one of these as `stream`.
