---
title: 'Headless integration'
icon: 'key'
description: 'Non-custodial trading for platforms: register sub-accounts under one principal, let Totalis build each transaction, sign it with your own key, and submit it back.'
---

In the headless model you hold the signing keys and Totalis never does. For every on-chain action,
Totalis builds the transaction and returns it unsigned. You sign it with the owner key and submit it
back. Totalis verifies the bytes, adds its own signatures, and broadcasts.

## At a glance

- One API principal, any number of sub-accounts. Each sub-account is a Solana public key you prove you control, with its own vault.
- Quoting is the public flow. Commit, build, submit and withdraw carry an `X-Subaccount` header.
- A build is single use and lives 90 seconds. Sign it as built, byte for byte.
- Signing is provider agnostic: a raw keypair, Privy, Turnkey, Fireblocks or hardware. Totalis needs one standard ed25519 signature.
- Preview. The surface is live but still changing. Confirm details with the team before you launch.

## Who it is for

Platforms that custody their own users and cannot hand each of them a Totalis login. You stay the
custodian of record and sign on their behalf. An individual holding their own Solana keypair can use
it too, as a single sub-account.

## Scopes

Use the `headless` preset when you mint the key: `POST /v1/api-keys` with
`{ "preset": "headless", "confirm_withdraw": true }`. It is the only preset that includes `tx:sign`
and `accounts:provision`. A key lacking a required scope is refused with `403 insufficient_scope`.

| Scope | Used for |
| --- | --- |
| `accounts:provision` | Register and disable sub-accounts |
| `account:read` | List and read sub-accounts |
| `markets:read` | Market reads from a scoped key. `GET /markets` itself is public |
| `trading:write` | Create and commit quote requests, build a position transaction |
| `tx:sign` | Submit a signed transaction |
| `positions:read` | Read quote requests and portfolio |
| `balances:read` | Read balances |
| `funds:withdraw` | Build and submit withdrawals |

<Accordion title="Every preset, expanded">
| Preset | Scopes |
| --- | --- |
| `read_only` | `account:read`, `markets:read`, `positions:read`, `balances:read` |
| `trading` | `read_only` plus `trading:write`, `funds:deposit` |
| `full` | `trading` plus `funds:withdraw`, `account:write`, `mm:quote`. No `tx:sign`, `keys:manage` or `accounts:provision` |
| `headless` | `trading` plus `funds:withdraw`, `tx:sign`, `accounts:provision`. No `keys:manage`, `account:write` or `mm:quote` |

The full catalog is `account:read`, `markets:read`, `positions:read`, `balances:read`, `trading:write`,
`funds:deposit`, `funds:withdraw`, `account:write`, `tx:sign`, `keys:manage`, `accounts:provision` and
`mm:quote`.
</Accordion>

## The loop

<Steps>
  <Step title="Browse markets">
    `GET /markets` is public and rate limited per IP. Take `markets[].ticker`, `markets[].venue` and
    the `exclusion_keys` you need to build legal legs. See
    [Limits and fees](/guides/limits-and-fees#parlay-construction).
  </Step>

  <Step title="Register a sub-account">
    Prove control of a public key in two calls: request a challenge, sign the exact bytes it returns,
    submit the signature. The returned `account.id` is the value you send as `X-Subaccount` from here on.

    <Accordion title="The calls">
    ```bash
    curl -X POST https://api.totalis.trade/v1/accounts/challenge \
      -H "X-API-Key: <key>" -H "Content-Type: application/json" \
      -d '{ "owner_pubkey": "<solana-pubkey>" }'
    # { data: { challenge_id, nonce, expires_at, message_to_sign } }
    ```

    `message_to_sign` is a base64 string of 152 canonical, domain separated bytes. Sign those bytes
    verbatim with strict RFC 8032 ed25519. Do not rebuild or re-encode them, and do not sign the nonce
    alone.

    ```ts
    import nacl from 'tweetnacl';
    const message = Buffer.from(challenge.message_to_sign, 'base64');
    const signature = nacl.sign.detached(message, ownerKeypair.secretKey);
    const control_proof = Buffer.from(signature).toString('base64');
    ```

    ```bash
    curl -X POST https://api.totalis.trade/v1/accounts \
      -H "X-API-Key: <key>" -H "Content-Type: application/json" \
      -d '{ "owner_pubkey": "<pubkey>", "challenge_id": "<id>", "control_proof": "<base64 signature>", "label": "your-user-ref" }'
    # { data: { account: { id, owner_pubkey, label, status, control_proved_at, created_at } } }
    ```

    | Endpoint | Purpose |
    | --- | --- |
    | `POST /v1/accounts/challenge` | Single use proof of control challenge |
    | `POST /v1/accounts` | Register the sub-account |
    | `GET /v1/accounts`, `GET /v1/accounts/{id}` | List or read sub-accounts |
    | `DELETE /v1/accounts/{id}` | Disable a sub-account. Funds stay withdrawable |
    </Accordion>
  </Step>

  <Step title="Fund the wallet">
    Hold native Solana USDC in the owner wallet's token account. There is no deposit call and you do
    not pre-transfer into the vault. The transaction Totalis builds for a trade includes the deposit.

    <Warning>
    Sending USDC straight into the vault's token account bypasses the program's accounting and does
    not count as a usable balance. Fund the wallet and let the trade move it.
    </Warning>
  </Step>

  <Step title="Quote and commit">
    Open a quote request under the principal, poll it until makers respond, then commit with
    `X-Subaccount` so the position is attributed to the right sub-account. Quote creation does not
    read the header; commit does.

    <Accordion title="The calls">
    ```bash
    curl -X POST https://api.totalis.trade/v1/quote-requests \
      -H "X-API-Key: <key>" -H "Content-Type: application/json" \
      -d '{ "legs": [ { "market_ticker": "<ticker-1>", "side": "yes", "venue": "kalshi" },
                      { "market_ticker": "<ticker-2>", "side": "no",  "venue": "kalshi" } ],
            "bet_amount": 50 }'

    curl https://api.totalis.trade/v1/quote-requests/<quote_request_id> -H "X-API-Key: <key>"
    # you need best_quote.id, quote_request.version and quote_request.book_seq

    curl -X POST https://api.totalis.trade/v1/quote-requests/<quote_request_id>/commit \
      -H "X-API-Key: <key>" -H "X-Subaccount: <account_id>" -H "Content-Type: application/json" \
      -d '{ "expected_version": <version>, "displayed_quote_id": "<best_quote.id>",
            "displayed_quote_book_seq": <book_seq>, "min_payout_odds_seen": <odds> }'
    # { data: { status: "committed", quote_request_id, rfq_id, quote_id, selected_payout_odds, confirmation_deadline } }
    ```
    </Accordion>

    Committing does not open the position. It reserves the maker's collateral and puts the position
    in `awaiting_signature`. You have about thirty minutes to build, sign and submit before it lapses
    and the collateral is released. Commit is idempotent per quote request and sub-account, so a retry
    returns the same `rfq_id`.
  </Step>

  <Step title="Build, sign, submit">
    Ask Totalis to build the transaction, sign its message with the owner key, and submit it with the
    same `build_id`.

    <Accordion title="The calls">
    ```bash
    curl -X POST https://api.totalis.trade/v1/positions/build-tx \
      -H "X-API-Key: <key>" -H "X-Subaccount: <account_id>" -H "Content-Type: application/json" \
      -d '{ "ticket_id": "<rfq_id>" }'
    # { data: { build_id, transaction } }
    ```

    `transaction` is a base64 `VersionedTransaction` with every signature slot empty. Deserialize,
    sign, re-serialize. With `@solana/web3.js`, `tx.sign([ownerKeypair])` fills only the owner's slot.

    ```ts
    import { VersionedTransaction } from '@solana/web3.js';
    const tx = VersionedTransaction.deserialize(Buffer.from(build.transaction, 'base64'));
    tx.sign([ownerKeypair]);
    const transaction = Buffer.from(tx.serialize()).toString('base64');
    ```

    ```bash
    curl -X POST https://api.totalis.trade/v1/wallet/submit-built-tx \
      -H "X-API-Key: <key>" -H "X-Subaccount: <account_id>" -H "Content-Type: application/json" \
      -d '{ "build_id": "<build_id>", "transaction": "<signed base64>" }'
    # { data: { tx_signature, position_id, status: "active" } }
    ```

    With a remote signer, sign `tx.message.serialize()` and place the 64 byte signature at the owner's
    account index. Do not change the message.
    </Accordion>

    <Warning>
    The built transaction is not broadcastable on its own. Totalis adds the maker and fee payer
    signatures inside submit, and only after the submitted message matches the built one byte for
    byte. A `build_id` is single use and lives about 90 seconds; if signing is slow, rebuild. If
    submit returns `submission_indeterminate`, do not resubmit blindly. Check the position or the
    chain first, since a blind retry risks a double create or a double withdraw.
    </Warning>
  </Step>

  <Step title="Settle and read">
    Positions settle server side at market resolution with no signature from you, and proceeds land
    in the sub-account's vault. Track sub-accounts with [webhooks](/_internal/partners/partner-console)
    and on-chain reads. The balance endpoints `GET /v1/wallet`, `GET /v1/vault` and
    `GET /v1/portfolio` report the calling principal's own account and ignore `X-Subaccount`.
  </Step>

  <Step title="Withdraw">
    Same build, sign, submit flow. Funds move from the vault to the owner wallet.

    <Accordion title="The call">
    ```bash
    curl -X POST https://api.totalis.trade/v1/vault/build-withdraw-tx \
      -H "X-API-Key: <key>" -H "X-Subaccount: <account_id>" -H "Content-Type: application/json" \
      -d '{ "amount": 50 }'
    # { data: { build_id, transaction } }, then sign and POST /v1/wallet/submit-built-tx
    ```

    `amount` is between `0.000001` and `1,000,000` USDC. Submitting a withdraw needs `tx:sign` and
    `funds:withdraw`. A confirmed withdraw build is final and cannot be resubmitted or rebuilt.
    </Accordion>
  </Step>
</Steps>

## Two ways to hold keys

Polling a quote request needs `positions:read`. A sub-account key minted from the
[partner console](/_internal/partners/partner-console) is clamped to `trading:write`, `tx:sign` and
`markets:read`, so it cannot poll or stream. Two patterns work:

| Pattern | How | Trade-off |
| --- | --- | --- |
| Split keys, for multi-tenant platforms | Poll and choose with a principal key that has `positions:read`. Commit, build and submit with the sub-account key. | The sub-account key can only ever act for its one account, so a leak is contained. |
| One principal key, for a single tenant | One `headless` key runs the whole loop. | It can build, sign and submit for any of your sub-accounts. You give up the per-account clamp. |

## Why a commit is refused

`details.reason` uses mixed casing. Branch on the exact strings.

| `details.reason` | Meaning |
| --- | --- |
| `QUOTE_EXPIRED` | No live quotes remain. Request a fresh quote |
| `QUOTE_CHANGED` | The version bumped or the odds slipped below your floor. Re-poll |
| `MARKET_NOT_LIVE` | A leg's market closed. Rebuild with live markets |
| `SUBACCOUNT_MISMATCH` | Already committed under a different sub-account |
| `NOT_ACTIVE` | The quote request is no longer active. Create a fresh one |
| `subaccount_key_mismatch` | A sub-account key was used for a different sub-account. Returned as `403` |
| `subaccount_not_found` | The sub-account id is not active for this principal |
| `subaccount_pending` | Control has not been proved or activated yet |
| `subaccount_disabled` | The sub-account is disabled |
| `mm_confirmation_timeout` | The maker did not confirm in time. Retry, optionally with `exclude_mm_ids` |
| `insufficient_mm_collateral` | No maker could back it. Retry |
| `awaiting_signature_cap` | This sub-account already has 25 unsigned positions. Sign or let some lapse |
| `awaiting_signature_principal_cap` | Your principal hit its aggregate unsigned ceiling. Sign or let some lapse |
| `quote_expired` | Lowercase core race variant of quote expiry. Request a fresh quote |
| `cancelled` | The committed ticket was cancelled before confirmation completed |
| `insufficient_balance` | Custodial path. Usually means `X-Subaccount` was omitted |
| `COMMIT_FAILED` | Unknown non-retryable core result. Re-poll or escalate |
| `COMMIT_FAILED_RETRYABLE` | Transient core failure, returned as `503`. Retry |
| `FORBIDDEN` | Core rejected the commit without a more specific public reason |

A malformed `X-Subaccount` returns `400` with the message `X-Subaccount must be a UUID`.

## What submit returns

| `details.reason` | Status | Meaning |
| --- | --- | --- |
| success | 201 | Position is active, or funds withdrawn |
| `build_expired` | 409 | The `build_id` is unknown or already used. Rebuild |
| `build_principal_mismatch` | 403 | The `build_id` belongs to another principal or sub-account |
| `byte_mismatch` | 400 | The submitted transaction does not match the built one. Rebuild and sign cleanly |
| `position_not_found` | 404 | No `awaiting_signature` position for this build |
| `rebuild_required` | 409 | The transaction did not land and the `build_id` is spent. Rebuild |
| `submission_indeterminate` | 500 | Outcome unknown. Check status before resubmitting |
| `insufficient_balance` | 400 | On a withdraw, the vault free balance is too low |
| `withdraw_scope_required` | 403 | The build is a withdraw and the key lacks `funds:withdraw` |
| `PARTNER_WITHDRAW_FORBIDDEN` | 403 | A withdraw submitted with a partner delegated key |
| `subaccount_disabled` | 409 | A create build for a disabled sub-account. Withdraws still work |

## Limits

- 25 positions in `awaiting_signature` per sub-account at once.
- An aggregate ceiling of unsigned positions per principal across all sub-accounts, 250 by default and environment tunable.
- Up to 1000 active sub-accounts per principal by default, environment tunable.
- Lapsed unsigned positions are cleaned up after about thirty minutes and their reserved collateral released.
- Build, submit and withdraw are limited to roughly ten requests per minute each. Everything else follows the buckets on [Limits and fees](/guides/limits-and-fees#rate-limits).
