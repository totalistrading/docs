A single trade crosses four channels. This is every lifecycle moment on all four, side by side.

Read a row to see one moment across every channel. Read a column to follow one channel start to
finish.

Field names, identifiers, and the aliases the same value travels under are in the
[Glossary](/guides/glossary). Event name grammar per channel is
[there too](/guides/glossary#event-naming).

<Note>
`quote:*` WebSocket events (`quote:accepted`, `quote:confirmed`, `quote:executed`, `quote:expired`,
`quote:rejected`, `quote:withdrawn`) deliver only to the awarded market maker, on their private
`mm:quotes:{mm_id}` channel. `position:*` events deliver on `rfq:{rfq_id}`, the channel a user or
anyone tracking a specific trade subscribes to.

The two families are not interchangeable views of the same moment. Several rows below have a
WebSocket event for the maker and nothing for the user, or the reverse.
</Note>

## The acquisition gap

An early cashout resolves one of two ways, and only one of them notifies you live.

### A closing exit is well covered

`position:bought_back` carries `rfq_id`, `position_pda`, `amount`, `mm_pays_user`, `tx_signature`,
and `quote_id`. It fans out to four places at once:

| Destination | Needs a subscription |
| --- | --- |
| The `rfq:{rfq_id}` channel, the canonical one for `position:*` events | yes, and this is the one to subscribe to |
| The `mm:quotes:{mm_id}` channel of the maker whose exposure closed | yes |
| Any connection authenticated as the seller | no, it arrives on identity alone |
| Any connection authenticated as that maker | no |

Because the last two arrive on identity alone, you may see the same event twice if you also hold the
`rfq:{rfq_id}` subscription. Dedupe on `tx_signature`.

The `position.bought_back` webhook carries the same moment for integrations that prefer webhooks.

### An acquiring bid notifies the buyer of nothing

<Warning>
When the winning bid comes from a market maker that was not the position's counterparty, the
position transfers to them and stays open. There is **no WebSocket event and no buyer-side webhook**
for that today. `position.transferred` is attributed to the seller.

If you bid on auctions for positions you do not already back, reconcile acquisitions from
[your position reads](/api-reference/mm/list-positions) rather than waiting for a push.
</Warning>

The RFQ status is not a fallback signal here either. A transfer leaves the position `executed`, so
polling for `bought_back` will never fire.

## Delivery guarantees

| Channel | Guarantee | On reconnect |
| --- | --- | --- |
| SSE | Live only, for the life of the request | Resume with `last_event_id` |
| WebSocket | Live only, no redelivery | Reconcile against [read endpoints](/guides/reading-data) |
| Webhooks | At-least-once, signed, retried | [Replay](/guides/webhooks#replaying-deliveries) by delivery id |
| REST | Current truth, on demand | n/a |
